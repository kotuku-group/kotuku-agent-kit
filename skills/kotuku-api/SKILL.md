# Kōtuku API Reference

Use the downloaded XML documentation as the authority for Kōtuku APIs. The documentation comes from the repository
declared in `references/kotuku-api-source.json` and records its exact revision locally.

## Lookup Workflow

1. Check for `references/docs/xml/modules/core.xml` and
   `../tiri-programming/references/wiki/Tiri-Reference-Manual.md`. If either is absent, run
   `origo <skill-directory>/scripts/fetch_reference.tiri --log-warning`, using the directory containing this
   `SKILL.md` as `<skill-directory>`. This refreshes the shared wiki and downloads the API documentation when needed.
   If the download fails, look for generated XML documentation in the consuming project's matching Kōtuku SDK
   checkout. If no authoritative local documentation is available, state that limitation and do not guess exact API
   details.
2. Read `references/documentation-map.md` for the downloaded layout and source revision.
3. Search `references/docs/xml/modules` for the exact module, class, action, method, field, constant, or error name.
4. Read the narrowest matching XML file. Class details are normally under
   `references/docs/xml/modules/classes`; module-level definitions are directly under `references/docs/xml/modules`.
5. Cross-check nearby definitions when ownership, inheritance, result ordering, or error behaviour is relevant.
6. If the project targets a different Kōtuku revision, prefer documentation generated by its matching SDK checkout
   and state the mismatch.

Do not infer that a conventional C++, Lua, browser, or POSIX API is available. Kōtuku object fields are case
sensitive, actions and methods can return an `ERR` result before ordinary values, and generated documentation may
describe lifecycle constraints that are not visible from a short signature.
